# Changelog

All notable changes to this repository are documented in this file.

Releases are versioned in lockstep across workspace members (`pipefy`, `pipefy-mcp-server`, `pipefy-cli`).

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Fixed

- **`uninstall.sh` (skills)**: a skill is removed only where a record says this toolkit installed it. Teardown deleted every `~/.claude/skills/pipefy-*` directory under a tier-1 label promising a reinstall would restore it, which is false for anything this repository does not ship: `pipefy-` is a namespace anyone may write in, and a skill someone authored there went through `remove_path` with no backup. The prefix is now read as a namespace rather than a claim of ownership. Provenance comes from two records and nothing else — the install receipt, which lists the skills a run added by difference against what was already there, and the lock file `skills add` keeps beside its store, whose `source` is compared for equality against this repository. Anything else under the same prefix is reported and left in place, including in heuristic mode, which is where most machines are and stay. A skill directory is usually a link into a shared store, so the store content and the lock entry now go with the link instead of being stranded behind a run that reported the skill gone. (#541)
- **`uninstall.sh` (hosted token)**: the hosted OAuth logout runs where it can reach its target. `claude mcp logout <name>` resolves the name across scopes and takes no scope flag, so running it in the credentials phase — before any registration was touched — bound it to whichever entry outranked the hosted one and failed, leaving the token stored. Removal now has a phase for unshadowing local- and project-scope registrations, then the logout, then the hosted entry itself; the credentials-before-configs-before-tools-before-skills-before-state order it sits inside is unchanged. A logout that fails is reported as failed with the in-client fallback, never as a cleared credential. (#541)
- **`uninstall.sh` (deletion guard)**: `remove_path` resolves a path before judging it. It compared strings after stripping trailing slashes, so `$HOME/..` was neither `/` nor `$HOME` as text and named the directory holding every account. Paths are now normalised — `.` and `..` cancelled, the surviving directory resolved through the shell so a symlink cannot hide behind it, the final segment deliberately left alone because a symlink is deleted as a link — and a path containing `$HOME` is refused alongside `/` and `$HOME` themselves. (#541)
- **`uninstall.sh` (marketplace clone)**: an `installLocation` read out of `known_marketplaces.json` is a claim to check, not a deletion target. With no marketplace CLI verb to delegate to, teardown deleted whatever absolute directory that registry named while the plan said only *unregister marketplace*. The path is now required to be the plugin directory's own clone, derived from the client table; anything else is reported and left, and the plan discloses the clone it will delete. (#541)
- **`uninstall.sh` (Codex sub-tables)**: `[mcp_servers.<name>.env]` is a separate table header, invisible to a scan that stops at the next `[`, so excising the parent section left the sub-table and its secrets behind while the closing re-scan reported Codex clean. A section with any dotted child table is now treated as hand-edited: both are reported, both stay, and the run does not claim the file is clear. (#541)
- **`install.sh` / `uninstall.sh` (JSON rewrites)**: `ensure_ascii=False` on every `json.dump`. Adding or removing one registration rewrote unrelated servers' UTF-8 values as `\uXXXX` escapes — semantically identical, and a change to a file the user did not ask to have rewritten. (#541)
- **`uninstall.sh` (receipt keys)**: the receipt reader accepts the hyphen its writer emits. `entry_created.claude-desktop` and `entry_created.claude-code` failed an `^[a-z][a-z0-9_.]*$` key check and were dropped as malformed, so the bit recording that a registration was already there never reached the decision, and teardown fell back to the heuristic and deleted an installer-shaped Claude Desktop entry the installer had explicitly recorded leaving alone. A parity test now expands the writer's key vocabulary over the advertised `--client` values and asserts the reader's alphabet accepts every one. (#541)
- **`uninstall.sh` (exit contract)**: a teardown that removed nothing while state remains no longer exits `0`. `Nothing to remove.` returned success on exactly the tree `--scan` exits `1` on — a hand-edited Codex section, a registration a receipt records as pre-existing — and skipped the report, so the *Left alone* notes explaining why nothing was planned never printed. Both now match `--scan`. (#541)
- **`uninstall.sh` (Linux keychain)**: a missing `secret-tool` reports the Secret Service as uninspected and exits `2`, as a missing `security` already did on macOS. A credential store nothing could read is not a store known to be empty, whatever the reason it could not be read. (#541)
- **`uninstall.sh` (`--client none`)**: the word is refused instead of silently disarming every registration edit. `--help` advertised `none` in the `--client` allowlist, inherited from `install.sh` where it means *install without registering*, but teardown narrows registration edits and nothing else — so `none` matched no client, skipped every config edit, and still removed the tools, leaving each registration the scan found pointing at a missing command. That is the stranding the phase order exists to prevent, and "tear down but touch no client config" has no coherent meaning, so the value is rejected with a message naming the difference rather than given a second one. The help text is generated from the client table alone. (#541)
- **`uninstall.sh` (skill store)**: a skill entry that links out of the store is not licence to delete what it points at. Resolving the link and deleting the target gave the teardown unbounded reach — a skill linked to a checkout of the user's own would have had that checkout removed — which is the marketplace `installLocation` problem with a longer arm. The permitted root is derived the same way the marketplace clone's is, from the lock file `skills add` keeps beside its store rather than from a hardcoded path, and both sides are canonicalized before the comparison. A target outside it leaves the link removed, the directory untouched, and a report line naming what stayed and where, so nothing reads as "the skill is gone" while its content is still on disk. (#541)
- **`uninstall.sh` (hosted token, reporting)**: an exit status is not proof for a store this run cannot read. `execute_plan` reported any action exiting `0` as `Removed:`, so a `claude mcp logout` that did nothing produced a verified removal claim, set the credential-deleted flag, and let the process exit `0` — with the client's OAuth store opaque to the closing re-scan, nothing ever contradicted it. The clear is now recorded as invoked-but-unobservable: its own report group, no removal claim, no credential-deleted accounting, and an exit of `1` rather than `0`, since a machine with an unverifiable clear is not one this run can call clean. This is the rule the local credential path already followed. (#541)
- **Skills (onboarding)**: the toolkit-setup skill's verify step uses the `curl` form of `uninstall.sh --scan`. It required `./uninstall.sh` at a repository root, which the hosted and plugin paths the skill leads with never produce. (#541)
- **`install.sh`**: a failed `uv tool install` is no longer swallowed. `run_quiet` read `$?` after the `if` that ran the command, which is the `if`'s own status (0) when its condition failed, so every failure reported success and the install carried on to register a server binary that was never installed. (#540)
- **`uninstall.sh` (matching rule)**: a registration is found whichever of its two fields identifies this toolkit, and a declared transport `type` is required for neither. An entry carrying a `url` and no `type` was treated as malformed and skipped, which is Claude Code's reading of that shape — it reads a type-less entry as stdio and refuses to start it — applied to every client. Cursor and Codex serve a bare `url` over HTTP, so a hosted registration in a Cursor config was invisible to the scan and survived a teardown, and the same shape was judged three different ways across the two client formats. An entry carrying both a `command` and a `url` diverged the same way in the other direction. The shape is now matched as written, described by whichever half is this toolkit's, and the per-client caveat comes from a `typed-remote` capability in the client table rather than from a client id in the matcher. The rule is implemented twice — python for the JSON configs, shell for the Codex TOML, which must work without python3 — and a suite drives one case table into both formats and one scan, so the copies cannot drift again. (#541)
- **CLI (`pipefy auth logout`)**: a stored keychain entry that exists but cannot be parsed — stale, corrupt, or written by an older schema — is now deleted instead of being reported as `Not signed in. Nothing to do.` while surviving on disk. The decision comes from entry **presence** (`session_entry_presence` in `pipefy_auth.storage`: `present` / `absent` / `unknown`) rather than from `load_session`, which collapses all three into one `None`. Revocation needs a readable refresh token, so an unreadable entry is delete-only and stderr says the token stays valid at the IdP until natural expiry. When the presence probe itself fails and nothing is deleted, the command claims neither removal nor a clean machine and exits 1. Revoke-failure warnings, the revoke-then-delete order, and the exit-1 manual-removal hint on a rejected delete are unchanged. (#538)
- **AI agents (active lifecycle)**: create can start inactive (`create_ai_agent(active=false)` / `pipefy agent create --inactive`) by sending `disabledAt` on create and the chained update so the second step does not revive; routine update preserves `disabledAt` (optional `disabled_at` / `--disabled-at` pass-through skips the re-read; use `toggle_ai_agent_status` / `pipefy agent toggle` to activate or deactivate); create/update success payloads expose `disabled_at` and `active`; partial-failure envelopes surface shell `disabled_at` and a toggle recovery hint. Skills document the contract. (#520)
- **Release workflow (validate, then publish)**: `.github/workflows/release.yml` created the GitHub Release before anything installed the wheels, so a failing smoke install left a published Release advertising artifacts that could not start. `v0.4.0-beta.1` was exactly that shape — the Release was created, the smoke install failed with `ModuleNotFoundError`, the PyPI upload was skipped, and withdrawing the Release and the tag was manual work. The job now runs in two bands: build, bound the wheel set, stage the PyPI set, and install it into a clean virtualenv launching every console entry point — and only then create the GitHub Release and upload to PyPI. A validation failure now leaves nothing behind but the tag, which is unavoidable because the tag is what triggers the workflow. PyPI stays last within the publish band, since an upload cannot be taken back while a Release can be deleted — which leaves one narrower gap by choice, a failing upload leaving a Release with no matching PyPI artifacts — and a comment in the file states the boundary so later validation is not added between the two publish steps. The two hand-rolled wheel-set assertions the job carried — an inline Python check on `dist/`, and a five-glob bash check while staging — collapse onto `smoke_entry_points.py --check-wheels`, already used by the CI and scheduled-smoke workflows, so every workflow reads one definition of the published-member list rather than three that can drift apart. Closes #535.
- **Release CLI (build before the boundary)**: `scripts/release.py publish` pushed the tag — the one irreversible step — without ever having built or installed the artifacts it was about to release. Every guard before the confirmation prompt was about repository state (branch, working tree, tag collision); the first time a wheel existed was on the CI runner, past the point of no return, and `verify` inspected the *published* result. `publish` now builds all five wheels with `uv build --all-packages --wheel` into a temporary directory, asserts one wheel per published member, installs them into a clean virtualenv, and launches every console entry point through `smoke_entry_points.py` — the same sequence the release workflow runs, moved to the side of the boundary where a failure costs nothing but a minute. The check sits in the shared irreversible half, after the repository-state guards so a wrong checkout still fails in a second rather than after a build, and before the confirmation prompt so the operator answers it knowing the artifacts start; nothing can reach a tag push without crossing it. A failure names which step broke and states that nothing was tagged, pushed, or published. `v0.4.0-beta.1` is the shape this catches: `mcp` 2.0.0 removed a module the MCP server imports at startup, so a fresh resolve produced a server that could not start — detectable locally in about a minute, and invisible in the release commit's diff, because nothing in the repository changed to cause it. Building into a temporary directory rather than `dist/` keeps a stale local build from being mistaken for a fresh one and leaves nothing behind. The confirmation prompt states that the built wheels install and launch, so what was checked is in front of the operator answering it. The check resolves third-party dependencies from PyPI rather than `uv.lock`, so it will occasionally pick a newer permitted version than the lock pins — that divergence is its subject, not a defect — and it needs the index, so a cut cannot be made while PyPI is unreachable. The wheel set `verify` requires on the GitHub Release is now derived from the published-member list in `smoke_entry_points.py` via a `wheel_stem` helper, so the escaped filename forms are no longer a hand-written third copy of that list. Closes #534.

### Added

- **CI / docs (shell script coverage and teardown documentation)**: `install.sh` and `uninstall.sh` are linted rather than trusted. `shellcheck --shell=sh` and `sh -n` run from `.pre-commit-config.yaml` and from a CI job that adds `dash -n`, since `/bin/sh` on macOS forgives what a Debian-family `/bin/sh` rejects; the hook comes from `shellcheck-py` so a contributor without Docker still gets it. A check asserts every `rm` and `rmdir` in `uninstall.sh` sits inside `remove_path`, and that the guard still refuses an empty argument, a relative path, `/`, and `$HOME`. A parity suite observes both scripts instead of reading them, snapshotting a fixture `HOME` around a real install and a real teardown per `--client`, so a file a new installer step writes has to be one teardown accounts for. A Linux round-trip job proves completeness against a real install with real network and real uv; its allowlist is explicit and each entry carries its reason. `docs/uninstall.md` documents the scan, the tiered teardown, heuristic mode, what is never removed by design, and the per-channel switching recipes; the removal one-liners scattered across the READMEs and the onboarding skill point at it, and the skill's prose invariant becomes a `--scan` run, in the `curl` form the hosted and plugin paths can actually reach. (#541)
- **`install.sh` / `uninstall.sh` (install receipt)**: `install.sh` appends one `key=value` record per run to `${XDG_STATE_HOME:-~/.local/state}/pipefy/install-receipt`, recording the `UV_TOOL_DIR` it used, whether it installed uv, whether it created each client registration or found one already there, where the skills landed, the release tag, and a schema version. It is installer state rather than user configuration, so it sits outside `~/.config/pipefy`, which holds the user's own `config.toml`. Each line is written as its step succeeds and the closing `record=end` marks a finished run, so a crashed install still leaves a usable record; records accumulate, so a second run with a different `--client` does not erase the first, and the merge takes the union of tool and skills directories because two runs with different `--prefix` both need tearing down. The format is parsed with POSIX text tools alone — teardown does not inherit the installer's python3 dependency — and a value carrying a space, an `=`, a tab or a newline round-trips through a defined escape. `uninstall.sh` prefers the receipt and falls back to heuristic mode when there is none: heuristic mode is permanent rather than transitional, since every install made before the receipt existed has none, and it removes less — in a config the installer writes it deletes a registration only where the value is exactly the single command the installer writes, and it never treats uv as this toolkit's. A record from an unknown schema is skipped whole rather than half-read, a malformed line is dropped, and no value from the receipt ever names something to delete: it only picks which tool directory to ask uv about, which skills directory to enumerate, and whether a registration the structural scan already found may be removed. The receipt is itself in the teardown inventory. Closes #540.
- **CI**: the `main` → `dev` back-merge pull request now opens itself (`.github/workflows/backmerge.yml`). Anything merged straight into `main` — a hotfix, a docs fix, a LICENSE — left `dev` behind until a human remembered to reconcile it, and nothing on the GitHub side noticed. `release-pr` refuses to cut while that is true, so forgotten drift did not corrupt a release; it blocked one, at the least convenient moment, for whoever happened to be cutting rather than whoever caused it. On every push to `main`, daily, and on demand, the workflow counts `origin/dev..origin/main` and, when it is non-zero, cuts `rc-dev/chore/back-merge-main-<short-sha>` from `origin/dev`, merges `origin/main` in, and opens a pull request into `dev`. The branch name is derived from the `main` head, which is what makes a re-run idempotent: the same drift resolves to the same branch, so an existing branch or pull request is recognized and left alone rather than pushed over — the ruleset blocks non-fast-forward pushes, and rewriting a branch under review destroys the reviewer's incremental diff. A *closed* back-merge pull request is neither reopened nor re-pushed, since closing one is a human decision, but its unresolved drift is recorded on the tracking issue rather than treated as handled — #564 and #565 were both closed without merging and the divergence then sat unnoticed for days. A conflict is treated as a normal outcome rather than an error: release drift conflicts on `CHANGELOG.md` by construction and binary assets conflict whenever both branches touched one, neither is resolvable automatically (`-X ours` and `-X theirs` both silently discard real work), so the merge is aborted, nothing is pushed, and an issue labelled `back-merge` carries the conflicting paths and the resolution commands. That issue is one thread found by its label, closes on its own once the branches are back in sync or when a later pull request answers it, and stays silent on a re-run that would say exactly the same thing. The run exits zero when either the pull request or the tracking issue landed, because a red X on every release trains people to ignore it — and non-zero when neither did, since exiting zero is defensible only while the issue is the compensating signal, and a green run that surfaced nothing at all is the silent drift this removes. The pull request carries no CI checks by default and says so plainly — GitHub does not trigger `on: pull_request` for a pull request opened with `GITHUB_TOKEN` — and a `BACKMERGE_TOKEN` secret turns checks on with no change to the workflow. The pull request body requires a **merge commit**: a squash or rebase discards the second parent, so `dev` gains the content of `main`'s commits but never their ancestry, the count never reaches zero, and the workflow reproposes the same back-merge forever. When a merged pull request is found alongside surviving drift, the tracking issue names the squash as the cause and gives the commands to redo it. The decision logic is unit-tested in `tests/test_backmerge.py`, and the `pull_request` trigger that exercises the workflow's own changes runs as a dry run, so editing it cannot open a genuine back-merge off the branch under review. Closes #561.
- **CI**: the packaging smoke install now also runs on a **daily schedule** (`.github/workflows/packaging-smoke.yml`), not only on push and pull request. `uv.lock` pins every dependency, so the suite passes against known-good versions no matter what is published, and this is the only gate that resolves from PyPI — which left the window between merges with no observer at all. A breakage published upstream armed itself with zero commits here and detonated on whatever release came next, regardless of content; `mcp` 2.0.0 was caught by the release workflow's own smoke step, after the tag was pushed and the GitHub Release created. Two jobs run, because they see different failures: wheels **built from the checkout** catch an upstream release outside the declared bounds (the failure that would land on the next release), and the wheels **already on PyPI**, installed by name the way a user installs them, catch a broken or incomplete upload plus upstream breakage against the bounds of the release that already shipped. A failure opens an issue labelled `packaging-smoke-failure`, or comments on the open one, so a break persisting across days stays one thread rather than a daily pile. Two limits are documented rather than solved: the schedule fires from the default branch only, so a change on `dev` is inert until promoted, and the gate proves process startup, not behaviour — a dependency release that breaks behaviour without breaking imports passes it, and the locked suite would not see it either. Closes #531.
- **CI**: `scripts/smoke_entry_points.py` becomes the single definition of "every published console entry point", shared by the CI, release, and scheduled-smoke workflows, which each carried their own launch list. It reads *installed* distribution metadata rather than the checkout, so it fails when a published member is missing from the install or when a wheel stops shipping its script — a wheel-filename glob could not see either. Its `--check-wheels` mode runs before the install and asserts one wheel per member, because an incomplete set is not an error for `pip`: the sibling `==` pins let it satisfy the absent member from the index, and the smoke then passes against a wheel the build never produced. Every discovered script is launched, so a newly added entry point is covered with no edit, while an explicit floor catches a lost one; the suite asserts both of its constants still match the workspace's `pyproject.toml` files, so adding a package or a script fails a test instead of quietly narrowing what the packaging gate checks.
- **Skills**: thin `pipefy-building` router (`skills/building/pipefy-building/`) maps build/configure intent to the correct domain skill; catalog and authoring domain list include `building`. Consulting-only `pipefy-process-design` links execution asks to the router instead of growing a delivery playbook.
- **Skills (Builder guardrails)**: `pipefy-automations` requires event×action `triggerEvents` checks before create, documents the known non-firing `field_updated` + `move_single_card` combo, and consolidates a did-not-fire / empty-logs debug checklist; `pipefy-ai-agents` (and AI automations) require an explicit AI ask plus post-write active/`disabledAt` re-read; `pipefy-ipaas` routes external-integration asks away from native automations/AI by default; `pipefy-pipes-and-cards` states phase connections are UI-only and requires verify-after-write before reporting success.
- **Release process**: alpha releases ship from `dev`, beta and stable releases from `main`. `scripts/release.py alpha-pr <bump>` branches off `origin/dev`, bumps the lockstep version, and opens a release PR into `dev`; once merged, `publish` from `dev` tags the commit and pushes the tag, whose wheels reach PyPI as a pre-release so the hosted MCP server's deployment wrapper can pin an exact version and exercise a release in staging before it ships. `release-pr beta` then promotes the alpha to the first beta of the same `X.Y.Z` (`0.5.0-alpha.3` -> `0.5.0-beta.1`) through the `dev` -> `main` release PR, and `publish` from `main` ships it. `alpha-pr` is `release-pr` based on `dev`, so both lines take the same reviewed path — a repository ruleset requires a pull request on `main` and `dev` alike, and no flow pushes a release branch: the bump always arrives via a merged PR and `publish` pushes only the tag, asserting the branch matches its remote so an unmerged release PR is reported as such. An alpha deliberately does not stamp `CHANGELOG.md`: `## [Unreleased]` keeps accumulating across `alpha.1..alpha.N` and is what the Release workflow uses as an alpha's release body, so the beta promotion still stamps the whole set into one section. Which branch a release ships from is derived from the version's own pre-release track rather than the operator's checkout, and enforced before the bump, again before the tag, and in the Release workflow itself, which asserts the tagged commit is an ancestor of `origin/dev` for an alpha or `origin/main` otherwise before any wheel is built.
- **SDK / MCP**: outbound Pipefy requests now carry the client **deployment** beside the surface, so hosted MCP traffic can be told apart from local installs. The two axes are orthogonal: the surface says which entry point ran (`mcp`, `cli`, `sdk`), the deployment says where it runs (`local`, `hosted`). With both, `User-Agent` reads `pipefy-sdk/<version> (<surface>; <deployment>)` and a parsed `X-Client-Deployment` joins the `X-Client-Name` / `X-Client-Version` pair, so a consumer never matches on the `User-Agent` string to group traffic. The MCP server derives the deployment from its resolved profile (`remote` → `hosted`, otherwise `local`) at the composition root: it is never read from env or TOML and no `PIPEFY_*_DEPLOYMENT` knob exists, keeping the property #336 established for the surface. Both sides are labelled explicitly, so a bare `(mcp)` unambiguously reads as a client older than this change rather than a local one — the one-time cost is that the existing `(mcp)` series is renamed rather than continued. The CLI keeps plain `(cli)` and sends no `X-Client-Deployment` (a CLI is local by definition), direct SDK use keeps plain `(sdk)`, and OAuth requests to the sign-in host are unchanged: the IdP path has neither a surface nor a deployment. Closes #550.

### Changed (breaking, internal API)

- **MCP**: ported to the `mcp` SDK 2.x (`mcp[cli]==2.0.*`), superseding both the `>=1.29.0,<2` floor bump and the `<2` cap entry listed below in this same cycle, whose closing note that the upper bound stays no longer describes the shipped pin. 2.0 removes the `mcp.server.fastmcp` module and renames `FastMCP` to `MCPServer`, so the pin could not move without the port. Nothing changes for a caller using the server over stdio or HTTP: the 187-tool surface, the `--toolsets` selections, the remote-safe floor, the tool-error envelope, and the structured log shapes are all unchanged, verified by the full suite plus a live smoke against the API. What changes is the code that embeds this package.
  - **The tool-call middleware seam moved onto the SDK's own.** The chain used to wrap the low-level server's private `request_handlers[CallToolRequest]` slot; 2.0 removes that dict and ships `MCPServer(middleware=[...])` instead. `install_tool_call_middleware` becomes `build_tool_call_middleware`, which returns one `ServerMiddleware` for the composition root to pass to the constructor. `extra_tool_middlewares` on `build_pipefy_mcp_server` is unchanged, so an embedder registering middleware needs no edit; an embedder that called `install_tool_call_middleware` directly does. Three shape changes for a middleware author. `ToolCallContext.req` is gone (read `tool_name` and `arguments`, now raw pre-validation values off the params). The seam's return type is the SDK's `HandlerResult` (`BaseModel | dict[str, Any] | None`) rather than a `types.ServerResult`, and a middleware that short-circuits returns the serialized wire dict `short_circuit_error` builds, not a model. And `ToolCallContext` carries a required `protocol_version`: `short_circuit_error` shapes its result against it, so any code constructing a context by hand (a middleware test fixture, a synthetic call) has to supply one.
  - **`serverInfo.version` now reports this package's version** (`pipefy_mcp.__version__`) instead of the SDK's. FastMCP neither accepted nor forwarded a version, so the advertised string tracked `mcp` itself; `MCPServer` takes one.
  - `host`, `transport_security`, and `json_response` leave the server constructor for the per-transport call, so `wire_hosted_observability` takes them. `port` is unaffected: it only ever reached the uvicorn bind. An embedder that calls `streamable_http_app()` itself must pass `json_response` there, or its POST replies become SSE-framed instead of plain JSON. `core/fastmcp_tool_lifecycle.py` is deleted in favour of the public `MCPServer.remove_tool`. `transport_security_for` pairs the resource-server URL parse with the allowlist build in one place.
  - **`context_from_request` is renamed `context_from_server_request`**, and its input changes from a `types.CallToolRequest` model to a `ServerRequestContext`. An embedder importing the old name from `pipefy_mcp.core.tool_middleware` gets an `ImportError`; the arguments and request id are read off the context (`ctx.params`, `ctx.request`) rather than off `req.params`.
  - **`McpRuntime.transport_security` is removed.** The SDK takes the DNS-rebinding allowlist per transport, on `streamable_http_app()`, so it no longer travels on the runtime; reading the attribute raises `AttributeError`. Resolve it with `transport_security_for(settings)` from `pipefy_mcp.core.transport_security` and pass the result to the serving call, as `run_server` does.
  - **What `call_next` returns inside a tool-call middleware is now polymorphic.** The SDK's own handler returns the serialized wire dict, keyed `isError` in camelCase, and so does `short_circuit_error`; a `CallToolResult` model, with a snake_case `is_error`, only arrives from an inner middleware that built its result by hand. Read the flag through `result_is_error(result)`, the supported accessor. A 1.x-style attribute read silently returns the default on the dict, so every real tool failure reads as a success. That exact read caused a regression during this port.
  - **A short-circuiting middleware owns its response envelope, and `short_circuit_error` now shapes one.** The SDK shapes a handler's result for the wire per negotiated revision *inside* the middleware chain, so a middleware that returns without awaiting `call_next` is never shaped. Returned as a `CallToolResult`, its 2.0 `resultType` default (`"complete"`, a 2026-07-28 field) reached the wire on a connection that negotiated 2025-11-25, invisibly, because a client's surface validation ignores unknown fields. `short_circuit_error` now takes the `ToolCallContext` as its first argument and returns the wire dict, shaped by the SDK's own `serialize_server_result` against `ctx.protocol_version`. A middleware author updates the call (`short_circuit_error(ctx, "quota exceeded", code="RATE_LIMITED")`); nothing changes for a client. `ToolCallContext` gains `protocol_version`.
  - A `tools/call` that names no tool is logged under `tool: "<unnamed>"` rather than an empty string, so it does not share a dashboard bucket with the real tool names. The call still reaches the middleware chain, and `ctx.tool_name` is still `""`, the raw view of what the client sent.
  - **Mounting the HTTP app carries a lifespan obligation.** The app `wire_hosted_observability` returns owns the lifespan that enters `session_manager.run()`. Serving it directly (what `run_server` does, and what a uvicorn deployment does) needs nothing extra. An embedder that `Mount`s it under a host Starlette or FastAPI app must enter `app.session_manager.run()` from the host's own lifespan, because Starlette does not run a mounted app's lifespan; skipping it leaves the session manager unstarted and every request fails.
  - The 4 MiB Streamable HTTP body limit (a `413` above it) carries forward from the 1.29.0 floor bump documented below, unchanged: the wiring passes no `max_request_body_size`, so the SDK default stands. Attachments are unaffected (no tool takes bytes or base64); a long free-text argument is the reachable case. A hosted deployment that needs a larger body raises it on the `streamable_http_app()` call.
  - **The pin is the 2.0 patch line, not `<3`.** Two of the surfaces this package builds on sit outside what SemVer covers: the `MCPServer(middleware=[...])` list, which upstream marks provisional, and the `Tool.run` patch behind the argument-validation envelope. A minor release can move either with no signal, and no CI job resolves past `uv.lock`, so nothing would catch it before a release. Patch releases are accepted; widening to a new minor is a deliberate change that re-tests both surfaces.
  - Transitive dependency changes worth noting for image builds: the SDK now uses `httpx2` rather than `httpx` (this package still declares `httpx` itself, and nothing hands an httpx object into the SDK), and adds `mcp-types`, `opentelemetry-api`, and `truststore` while dropping `httpx-sse`. `truststore` validates TLS against the OS trust store, so a minimal container with no system CA store needs `SSL_CERT_FILE`. **Two transitive majors arrive together:** `starlette` 0.46.1 to 1.3.1 and `sse-starlette` 2.2.1 to 3.4.6. `starlette` is now a declared dependency of `pipefy-mcp-server` (`starlette>=1.3.1,<2`) rather than an undeclared transitive, because four modules import it directly (the `Starlette` app `wire_hosted_observability` returns, and the `Request` annotation on `McpRuntime.session_for_request` and the two identity resolvers), so an SDK release that dropped or vendored it would have broken those imports with no bound to catch it. `uvicorn` is now declared for the same reason (`uvicorn>=0.34.0,<1`): `run_server` imports it and builds the `Config`/`Server` pair on the `--transport http` path, while the SDK requires it only under a `sys_platform != 'emscripten'` marker, so the transitive guarantee was conditional.
  - The SDK deprecates the logging capability in the 2026-07-28 revision (SEP-2577), so every `ctx.debug` call in the tool modules emits `MCPDeprecationWarning` — around a thousand warning records in a suite run, against a previously clean baseline. Migrating those calls is a behavior change deserving its own review, so the suite carries one scoped `filterwarnings` ignore instead, matched on the message rather than the class so the SDK's other deprecation subjects still surface. The ignore is bounded by construction: when the SDK removes the capability the calls break outright and the suite fails regardless.
  - Part of #543. **The server negotiates `2025-11-25` on the `initialize` handshake, but a client that opens with the enveloped `server/discover` reaches `2026-07-28`**, which a default `mcp` 2.x `Client` (`mode="auto"`) does. Adopting that revision as the served default is still separate work; what changed here is that the tools now behave correctly on both.

## [0.3.0-alpha.1] - 2026-07-04

### Added

- **MCP**: opt-in OAuth 2.0 resource-server profile for the `remote` HTTP profile. Setting `PIPEFY_MCP_RS_RESOURCE_SERVER_URL` activates it (no separate enable flag): the server validates an inbound `Authorization: Bearer` on every request (RS256 against the issuer's JWKS, issuer and expiry, optional audience), serves RFC 9728 protected-resource metadata, and returns `401` with a `WWW-Authenticate` challenge on a missing or invalid token. Token-validation knobs live in `pipefy_auth.JwtValidationSettings` (`PIPEFY_JWT_ISSUER_URL`, which defaults to the login issuer, plus `PIPEFY_JWT_AUDIENCE` / `PIPEFY_JWT_VERIFY_AUDIENCE` / `PIPEFY_JWT_JWKS_URI`); resource identity (`PIPEFY_MCP_RS_RESOURCE_SERVER_URL`, `PIPEFY_MCP_RS_REQUIRED_SCOPES`) stays in `pipefy_mcp.ResourceServerSettings`; `PIPEFY_ALLOW_INSECURE_URLS` covers both. The stdio profile is unchanged. Closes #301.
- **MCP**: the `remote` resource-server profile now acts on behalf of the validated caller (#302). An app-scoped runtime owns one shared, auth-agnostic engine (the shared GraphQL endpoints and schema cache) and opens a cheap per-request session bound to the caller's identity: the hosted profile snapshots the request's validated bearer into that session, so one server serves concurrent callers as themselves rather than as a single startup identity. Credential resolution and its fail-fast move to the composition root (`McpRuntime.for_profile` / `StartupIdentity.from_configured_credential`); the stdio profile still runs as the one credential resolved at startup. Closes #302.
- **SDK**: `PipefyEngine`, a process-scoped, auth-agnostic core holding the shared GraphQL endpoints and their schema cache. Build one per process with `PipefyEngine.build(settings)`, then call `engine.session(auth)` per request for a cheap, identity-bound `PipefyClient`. This separates process-scoped wiring (endpoints, schema cache) from per-request identity, so serving many callers reuses one schema cache while each acts as itself; a future auth transform (OBO exchange, a distinct downstream audience) becomes a change to the `auth` passed to `session`, not to the engine.
- **SDK / MCP / CLI / auth**: outbound Pipefy requests now carry client-identifying telemetry headers so the API can attribute traffic by surface and version. The GraphQL path (public, Interfaces, and Internal API endpoints) sends `User-Agent: pipefy-sdk/<version> (<surface>)`, `X-Client-Name: <surface>`, and `X-Client-Version: <version>`, where `<surface>` is `mcp`, `cli`, or `sdk`. The surface is stamped programmatically at each entry point's composition root: the MCP server passes `mcp`, the CLI `cli`, and direct SDK use keeps the `sdk` default. It is a `PipefyClient` constructor argument rather than configuration, so it is never read from env or TOML and a caller cannot forge it. OAuth requests to the sign-in host carry `User-Agent: pipefy-auth/<version>`, `X-Client-Name: auth`, and `X-Client-Version`, identifying the auth component rather than an API surface. The header builder lives in `pipefy_infra.telemetry` so the SDK and auth packages share one `User-Agent` format. Closes #336.
- **CLI**: `pipefy table field create|update|delete` manage database table columns, closing the three deferred table-field rows in the MCP↔CLI parity matrix (`create_table_field`, `update_table_field`, `delete_table_field`). `create` takes positional table id plus `--label`/`--type` (with `--extra` for other `CreateTableFieldInput` keys). `update` sends only provided keys via `--label`, `--description`, `--required`, `--options`, or `--extra` (`--table` recommended, required by the API). `delete` is destructive (`--yes` or interactive confirm; `--table` required).

### Changed

- **SDK**: PyPI distribution renamed from `pipefy-sdk` to `pipefy` (the previous name is refused by PyPI as too similar to the unrelated `pipefysdk`). - **MCP (breaking)**: replaced the `--remote` launch flag with two explicit, orthogonal flags: `--profile {local|remote}` (env `PIPEFY_MCP_PROFILE`) and `--transport {stdio|http}` (env `PIPEFY_MCP_TRANSPORT`). The `PIPEFY_MCP_REMOTE_MODE` env var and the `McpSettings.remote_mode` field are removed; the default-deny remote-safe tool surface now follows `profile == "remote"`. `local` (default) registers every tool; `remote` exposes only the remote-safe surface and validates an inbound bearer per request when a resource-server URL is set. - **SDK**: `PipefyClient` now constructs its internal API client during `__init__` (built from the same `settings` and `auth` as every other endpoint client), so `PipefyClient(settings, auth=...)` is fully wired after construction. The `PipefyClient.internal_api_available` property is also removed: the internal API client is always present, so the property was always `True`.
- **Auth (breaking)**: `resolve_pipefy_auth` now returns a `ResolvedAuth` sum type (`StaticTokenAuth | ServiceAccountAuth | StoredSessionAuth`) instead of an `httpx.Auth`. ### Removed

- **Auth (breaking)**: removed the unused `CallableBearerAuth` httpx adapter and its `pipefy_auth` export. It had no production construction site; `RefreshableBearerAuth` already covers the per-request-provider behaviour (re-calling the token provider each request) plus the 401 refresh-and-retry the stored-session path needs.
- **Auth (breaking)**: removed `pipefy_auth.tier_for` and the internal `_TIER_BY_AUTH_TYPE` reverse-lookup table. ### Fixed

- **CLI**: `pipefy agent update` resolves slug-style `fieldId` values in behaviors for error-path enrichment the same way as the happy path (via `PipefyClient.update_ai_agent`), so `RECORD_NOT_SAVED` diagnostics do not falsely blame slug tokens as unknown pipe fields.
- **CLI / MCP**: `field-condition create` / `update` accept legacy `actionId: "hidden"` on condition actions; the SDK normalizes to `hide` before mutations.
- **SDK**: `PipeConfigService.update_phase_field` accepts optional `phase_id` / `pipe_id` and resolves a slug-like `field_id` to the field's `uuid` (injected as `input.uuid` while the slug stays as `input.id`, matching Pipefy's `UpdatePhaseFieldInput` contract). The pipe-wide lookup runs phase fetches concurrently via `asyncio.gather`; partial phase-fetch failures raise an actionable `ValueError` instead of returning an ambiguous match. Surfaced through MCP `update_phase_field(phase_id=…, pipe_id=…)` and CLI `pipefy field update --extra '{"phase_id":"…"}'`.
- **MCP**: `delete_phase_field` preview now enumerates `dependents.field_conditions` even when the rule only references the field in expression `field_address` (not just `actions[].phaseFieldId`); the condition tree walker has a defensive depth cap of 16.
- **SDK / MCP**: `PipefyClient.get_automation_logs_by_repo` short-circuits to an empty page when the pipe has no automations (was returning `MULTIPLE_INVALID_INPUT: Automation_ids can't be blank` from the API).
- **SDK / MCP**: `invite_members` validates each row with a new `MemberInvite` Pydantic model (`EmailStr` + non-blank `role_name`, lowercase normalization, `extra="forbid"`) and raises a single-line `ValueError` pointing at the offending field. MCP surfaces it as `INVALID_ARGUMENTS`.
- **SDK**: `ai_preflight.validate_ai_automation_prompt_sdk` flags overlap when the same `%{internal_id}` appears both in the prompt and in `field_ids`, in English, citing the API rejection message.
- **MCP**: `find_records` returns the unified envelope `pagination={has_more, end_cursor, page_size}` (snake_case) when the unified envelope flag is on, matching `get_table_records`.
- **MCP / CLI docs**: `create_card`, `create_table_record`, `clone_pipe`, and `create_field_condition` docstrings clarify title-derivation quirks, async clone phases, and the `phaseFieldId` discovery path.
- **SDK**: `MemberInvite` lives at `pipefy_sdk.MemberInvite` (re-exported in the top-level `__all__`); `slug_like_field_token` / `looks_like_uuid_token` extracted to `pipefy_sdk.utils.field_tokens` for reuse across services.
